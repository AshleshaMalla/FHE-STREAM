# FHE-RaiderSTREAM: Benchmark Architecture

## 1. Architecture Overview

FHE-RaiderSTREAM is a multi-backend memory bandwidth benchmark for OpenFHE.
Its purpose is to isolate *where* performance is lost in the FHE software
stack — hardware, math, software abstraction, or network — by measuring each
layer independently.

The suite is built around a multi-target CMake architecture controlled by three
feature flags:

| Flag                | Default | Effect                                       |
|---------------------|---------|----------------------------------------------|
| `ENABLE_DCRT`       | `ON`    | Builds the raw DCRTPoly polynomial backend.  |
| `ENABLE_CIPHERTEXT` | `OFF`   | Builds the high-level Ciphertext backend.    |
| `ENABLE_MPI`        | `ON`    | Links MPI and enables distributed kernels.   |

Each backend uses its own Google Benchmark **Fixture** (`FHERaiderSTREAM` for
DCRT, `CTFixture` for Ciphertext) with dedicated `SetUp` / `TearDown`
lifecycle hooks that allocate and destroy the working set.  All parameter
combinations (RingDim × Depth × BatchSize) are generated by a shared
`RaiderSTREAM_Arguments` function.

## 2. The DCRTPoly Backend (Hardware & Math Limits)

**Fixture:** `FHERaiderSTREAM` (backed by raw `NativePoly` / `NativeInteger`
vectors — no `shared_ptr`, no metadata, no allocator overhead).

This backend answers the question: **"How fast *can* the hardware move FHE
data?"**

### 2.1 Sequential Kernels (`RS_SEQ_*`)

These are the STREAM-style contiguous-access kernels.  They establish the
**raw hardware memory bandwidth ceiling** — the "Speed Limit" — against which
every other kernel is compared.

| Kernel          | Operation              | Bytes Model (per element)    |
|-----------------|------------------------|------------------------------|
| `RS_SEQ_COPY`   | `C[i] = A[i]`          | 2 polys (read A, write C)    |
| `RS_SEQ_SCALE`  | `B[i] = scalar * C[i]` | 2 polys (read C, write B)    |
| `RS_SEQ_ADD`    | `C[i] = A[i] + B[i]`   | 3 polys (read A+B, write C)  |
| `RS_SEQ_TRIAD`  | `A[i] = B[i] + s*C[i]` | 3 polys (read B+C, write A)  |

### 2.2 Gather Kernels (`RS_GATHER_*`)

Gather kernels read data through an indirection index array:
`C[i] = A[idx[i]]`.  They measure the **strided access penalty** and **TLB
miss rate** that occurs in real FHE automorphisms — without triggering the
key-explosion overhead of loading Galois keys.

| Kernel            | Pattern                        |
|-------------------|--------------------------------|
| `RS_GATHER_COPY`  | `C[i] = A[idx[i]]`            |
| `RS_GATHER_SCALE` | `B[i] = scalar * C[idx[i]]`   |
| `RS_GATHER_ADD`   | `C[i] = A[idx[i]] + B[idx[i]]`|
| `RS_GATHER_TRIAD` | `A[i] = B[idx[i]] + s*C[idx[i]]` |

### 2.3 Scatter Kernels (`RS_SCATTER_*`)

Scatter kernels write through an indirection array: `C[idx[i]] = A[i]`.
They measure the **random-write penalty** (store-buffer pressure, cache-line
conflicts).

| Kernel             | Pattern                        |
|--------------------|--------------------------------|
| `RS_SCATTER_COPY`  | `C[idx[i]] = A[i]`            |
| `RS_SCATTER_SCALE` | `B[idx[i]] = scalar * C[i]`   |
| `RS_SCATTER_ADD`   | `C[idx[i]] = A[i] + B[i]`     |
| `RS_SCATTER_TRIAD` | `A[idx[i]] = B[i] + s*C[i]`   |

### 2.4 Scatter-Gather Kernels (`RS_SCATTER_GATHER_*`)

Combined random-read + random-write. These model the worst-case permutation
patterns found inside FHE slot rotations.

| Kernel                    | Pattern                                    |
|---------------------------|--------------------------------------------|
| `RS_SCATTER_GATHER_COPY`  | `C[idx2[i]] = A[idx1[i]]`                 |
| `RS_SCATTER_GATHER_SCALE` | `B[idx2[i]] = scalar * C[idx1[i]]`        |
| `RS_SCATTER_GATHER_ADD`   | `C[idx2[i]] = A[idx1[i]] + B[idx1[i]]`    |
| `RS_SCATTER_GATHER_TRIAD` | `A[idx2[i]] = B[idx1[i]] + s*C[idx1[i]]`  |

### 2.5 NTT Round-Trip (`RS_NTT_ROUNDTRIP`)

Performs a forward NTT followed by an inverse NTT on every polynomial in the
working set.  Measures the **in-place butterfly bandwidth**, limited by L1/L2
cache line reuse.

### 2.6 KeySwitch Mock (`RS_KEYSWITCH_MOCK`)

```
A[i] = A[i] + B[i] * C[0]
```

A simulated fused multiply-add (FMA) kernel that streams two massive arrays
(`A`, `B`) while multiplying against a single L1-cache-resident "digit"
(`C[0]`).  This models the inner loop of BFV `KeySwitch` — where the
polynomial is decomposed into digits and each digit is multiplied by a column
of the evaluation key.

It measures the **"Cryptographic Math Tax"**: the cost of compute-bound FMA
on data with zero temporal locality.  When this kernel saturates memory
bandwidth at a *lower* throughput than `RS_SEQ_ADD`, the gap reveals how much
bandwidth is wasted on arithmetic that the ALUs cannot retire fast enough.

**Bytes model:** 3 polys per element (read A + B, write A).

## 3. The Ciphertext Backend (Software & Capacity Limits)

**Fixture:** `CTFixture` (uses full `Ciphertext<DCRTPoly>` objects managed by
`CryptoContext`, complete with `shared_ptr` wrappers, metadata, and dynamic
allocation).

This backend answers the question: **"How much bandwidth does the OpenFHE
*software* layer cost?"**

All byte counters report only **payload polynomials** (the `(a, b)` ring
elements inside each ciphertext).  This "**Goodput**" metric deliberately
excludes metadata, vtable pointers, and allocator overhead so that the gap
between DCRTPoly throughput and Ciphertext throughput directly quantifies the
software tax.

### 3.1 Sequential Kernels (`CT_SEQ_*`)

| Kernel               | Operation                                  | Bytes Model            |
|----------------------|--------------------------------------------|------------------------|
| `CT_SEQ_COPY`        | `C[i] = Clone(A[i])`                      | 2 ct (4 polys)         |
| `CT_SEQ_ADD`         | `C[i] = EvalAdd(A[i], B[i])`              | 3 ct (6 polys)         |
| `CT_SEQ_SCALE`       | `B[i] = EvalMult(C[i], plaintext_scalar)`  | 2 ct (4 polys)         |
| `CT_SEQ_TRIAD`       | `A[i] = EvalAdd(B[i], EvalMult(C[i], s))` | 3 ct (6 polys)         |

These measure the **"Software Tax"** — the overhead of `std::shared_ptr`
reference-count chasing, ciphertext metadata copies, and the OS memory
allocator (`malloc`/`free`) that sits between the algorithm and the hardware.

Comparing `CT_SEQ_ADD` throughput to `RS_SEQ_ADD` throughput at the same
RingDim and Depth directly reveals how much bandwidth the C++ abstraction
layer destroys.

### 3.2 In-Place Add (`CT_SEQ_ADD_INPLACE`)

```
EvalAddInPlace(C[i], A[i])
```

**Bytes model:** 2 ct (4 polys — read A, read+write C).

This kernel exists to measure **how much performance is recovered by
eliminating the allocator**.  `EvalAdd` allocates a new ciphertext on every
call; `EvalAddInPlace` writes directly into the existing buffer.  The
throughput difference between `CT_SEQ_ADD` and `CT_SEQ_ADD_INPLACE`
isolates the cost of `malloc` in the hot path.

### 3.3 Multiplication Without Relinearization (`CT_SEQ_MULT_NO_RELIN`)

```
C[i] = EvalMultNoRelin(A[i], B[i])
```

**Bytes model:** 7 polys (read A: 2, read B: 2, write C: 3 — a degree-2
ciphertext has 3 ring elements).

Measures the raw tensor-product cost without key-switching.  The output is a
degree-2 ciphertext that can be fed to `CT_SEQ_RELIN`.

### 3.4 Relinearization (`CT_SEQ_RELIN`)

```
C[i] = Relinearize(A_deg2[i])
```

**Bytes model:** 5 polys (read A_deg2: 3, write C: 2).

This kernel measures the **"Capacity Wall."**  Relinearization must stream
Gigabyte-sized evaluation keys from main memory for every ciphertext.  By
using a pre-computed degree-2 input (`ct_A_deg2`, prepared by
`EvalMultNoRelin` during `SetUp`), this kernel isolates the exact bandwidth
destruction caused by streaming relinearization keys — separated from the
multiplication itself.

At high multiplicative depths (e.g., depth 40), the evaluation key set alone
can exceed the LLC capacity, causing every `Relinearize` call to thrash the
entire cache hierarchy.

## 4. The MPI Extension (The Network Wall)

When compiled with `ENABLE_MPI=ON` and launched under `mpirun`, every kernel
automatically inserts `MPI_Barrier` synchronization and aggregates throughput
across ranks via `AggregateBandwidth()` (an `MPI_Reduce` sum on Rank 0).

### 4.1 `CT_MPI_SENDRECV`

A synchronous Rank-0 → Rank-1 ping-pong benchmark:

1. **Rank 0** serializes each ciphertext via `Serial::Serialize(..., BINARY)`,
   sends the size (`MPI_UINT64_T`) followed by the payload (`MPI_CHAR`).
2. **Rank 1** receives the size, allocates a buffer, receives the payload,
   and deserializes via `Serial::Deserialize`.
3. **Rank 1 reports 0 bytes** to prevent double-counting when
   `AggregateBandwidth` sums across ranks.
4. Registration uses `->Iterations(10)` to force both ranks into identical
   iteration counts, preventing the Google Benchmark auto-calibration
   deadlock on paired `MPI_Send`/`MPI_Recv` calls.

**Bytes model:** 2 polys per ciphertext (payload only — the serialized
metadata envelope is deliberately excluded).

This kernel explicitly measures the **"Serialization Tax"** — the cost of
converting a live C++ ciphertext object into a flat byte stream before data
even touches the NIC.  In distributed FHE pipelines, this serialization
overhead frequently dominates end-to-end latency and chokes horizontal
scaling.

## 5. Build and Run Reference

All commands assume you are in the `fhe-raiderstream/` project root.

### 5.1 Build — DCRT Only (Default)

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
```

### 5.2 Build — DCRT + Ciphertext + MPI

```bash
cmake -S . -B build \
  -DCMAKE_BUILD_TYPE=Release \
  -DENABLE_CIPHERTEXT=ON \
  -DENABLE_MPI=ON
cmake --build build -j
```

### 5.3 Run — Local DCRT Test

```bash
RS_BATCH_SIZE=40 ./build/fhe_raiderstream \
  --benchmark_filter="RS_SEQ_ADD/32768/5"
```

### 5.4 Run — Local Ciphertext Test

```bash
RS_BATCH_SIZE=2 ./build/fhe_raiderstream \
  --benchmark_filter="CTFixture/CT_SEQ_ADD/16384/5" \
  --benchmark_min_time=0.05s
```

### 5.5 Run — Distributed MPI Test (2 Local Ranks)

```bash
RS_BATCH_SIZE=2 mpirun -np 2 ./build/fhe_raiderstream \
  --benchmark_filter="CTFixture/CT_MPI_SENDRECV/16384/5"
```

### 5.6 Run — Distributed MPI Test (Multi-Node with Hostfile)

Create a `hostfile` listing one host per line:

```
node0 slots=1
node1 slots=1
```

Then run:

```bash
RS_BATCH_SIZE=2 mpirun --hostfile hostfile -np 2 ./build/fhe_raiderstream \
  --benchmark_filter="CTFixture/CT_MPI_SENDRECV/16384/5"
```

### 5.7 Environment Variables

| Variable        | Default | Description                                            |
|-----------------|---------|--------------------------------------------------------|
| `RS_BATCH_SIZE` | `100`   | Number of ciphertexts / polynomials in the working set.|

> **Memory warning:** Each ciphertext at RingDim=131072, Depth=40 is ~240 MB.
> At `RS_BATCH_SIZE=100` that is ~24 GB per array (×3 arrays = ~72 GB).
> Use `RS_BATCH_SIZE=2` on memory-constrained machines.

### 5.8 Useful `--benchmark_filter` Patterns

```bash
# All sequential DCRT kernels at RingDim 32768
--benchmark_filter="RS_SEQ_.*/32768"

# All ciphertext kernels
--benchmark_filter="CTFixture/.*"

# Only the relinearization kernel at depth 20
--benchmark_filter="CT_SEQ_RELIN/.*/20"

# The MPI send/recv kernel across all parameter combos
--benchmark_filter="CT_MPI_SENDRECV"
```
